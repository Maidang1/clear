# ADR 0003：健康概览的优先级与数据完整性

- 状态：已接受
- 日期：2026-07-31
- 决策来源：[定义健康概览的跨模块优先级与数据完整性语义](https://github.com/Maidang1/clear/issues/11)

## 背景

内存压力、磁盘空间、启动项影响和可卸载应用没有共同的自然单位。把它们压成一个总分会制造精度错觉；完全不排序又无法兑现健康概览“先解释最值得关注的状态”的承诺。权限、接口或时效造成的数据缺口也不能被解释成健康。

## 决策

每个模块输出一个 `ModuleDigest` 概念模型：

- 一句有范围限定的状态文案；
- 一个离散关注级别；
- 一个关键指标和支持该判断的证据；
- 独立的数据完整性；
- 观测时间和观测代次；
- 一个上下文相关的安全下一步。

健康概览不产生总分，不对不同单位求和，也不把“可释放字节”直接当作风险。

### 关注级别

| 等级 | 语义 | 文案基线 |
| --- | --- | --- |
| `actNow` | 已确认存在当前、时间敏感且有安全下一步的影响 | “建议现在查看” |
| `review` | 已确认存在有意义、可处理但不紧急的机会 | “有可处理项” |
| `observe` | 有值得继续观察的信号，但当前不建议处理 | “继续观察” |
| `clear` | 在完整且新鲜的观测范围内没有诊断发现 | “未发现需处理项” |
| `undetermined` | 关键数据不足，不能形成模块判断 | “数据不足，无法判断” |

模块规则只能依据可观察证据产生等级。启动项和应用卸载不是恶意软件扫描器，不得把“未知发布者”“长期未用”等单一信号包装成安全威胁。

### 数据完整性

数据完整性保存结构化的已观测范围、受阻范围、能力缺口、观测时间和新鲜度，再投影为：

- `complete`：模块要求的范围均在时效内成功观测；
- `partial`：部分范围受阻，但已观测范围仍能支持有限判断；
- `stale`：曾成功观测但已超过模块时效；
- `unavailable`：关键来源不可用，无法形成判断。

关注级别和数据完整性不相互覆盖：

- 完整性为 `partial` 时，已确认发现仍可显示，但文案必须限定为“在已扫描范围内”。
- `partial` 且没有发现时不能显示 `clear`，只能说明已扫描范围内未发现，并暴露缺口。
- `stale` 数据不能直接进入安全事务；下一步先刷新。
- `unavailable` 对应 `undetermined`，不能降级成“正常”。

### 默认选择与下一步

默认展开模块使用不可见的词典序呈现优先级，而不是数值评分：

1. 具有新鲜证据的 `actNow`；
2. 具有新鲜证据的 `review`；
3. 阻止形成判断的重要数据缺口；
4. `observe`；
5. 完整且新鲜的 `clear`。

同级先选择时间敏感性更高、最近发生状态变化的模块；仍相同时使用固定模块顺序保证界面稳定。用户手动选择后不因后台采样抢走焦点。

唯一下一步按上下文选择：

- 已确认发现：查看候选范围或事务预览；
- 关键权限缺口：了解并由用户主动开启对应能力；
- 数据过期：刷新；
- 完整且无发现：进入模块详情。

颜色和图标只能辅助，状态句、范围和观测时间必须以文本呈现。

## 备选方案

### 0–100 健康总分

拒绝。权重不可证实，缺失数据容易被当作零风险，且会诱导用户为提高分数执行无意义处理。

### 只按可释放字节排序

拒绝。它无法比较内存压力、启动影响和数据完整性，也会奖励体积大但价值低的处理。

### 数据不全时隐藏整个模块

拒绝。隐藏会把权限或能力缺口伪装成没有问题。

## 影响

- 四个模块必须输出相同形状的摘要，但保留自己的证据和阈值。
- `HealthDigest` 的排序逻辑需要纯函数测试，覆盖缺失数据、状态变化和用户手动选择。
- 健康概览必须显式显示范围限定、观测时间和权限缺口。
- 各模块地图需要分别确定产生关注级别的证据阈值和新鲜度门槛。
