# ADR 0001：跨模块统一安全事务

- 状态：已接受
- 日期：2026-07-31
- 决策来源：[定义跨模块统一安全事务与恢复语义](https://github.com/Maidang1/clear/issues/7)

## 背景

Clear 需要用同一套产品承诺覆盖退出应用、移动文件到废纸篓、禁用启动项和卸载应用。这些操作的目标身份、可逆性和验证方式不同。如果每个模块自行定义确认、错误和恢复语义，用户无法判断一次处理是否真的完成，崩溃后也容易误重放副作用。

## 决策

所有产生副作用的操作都实现同一个不可变安全事务契约。事务由以下阶段组成：

1. `previewed`：生成事务预览，绑定事务 ID、模块、操作类型、目标身份、观测代次、证据、预期影响、权限需求、逐项目风险、可逆性和恢复路径。
2. `confirmed`：用户确认的是事务预览的摘要值，不是抽象操作名称。任何目标集合、风险、权限或预期影响变化都会使确认失效。
3. `preflighting`：执行前逐项重新观察目标身份、权限和前置条件。变化的项目拒绝执行并要求重新预览；不得用旧确认覆盖新状态。
4. `executing`：只执行通过复验的项目。每个副作用前写入 journal 意图，之后写入可观察结果。
5. `verifying`：用独立于执行返回值的观察确认最终状态。
6. `completed`、`partiallyCompleted`、`failed` 或 `uncertain`：逐项记录最终状态、证据、错误和恢复路径。
7. `reconciling`：启动时只观察未完成 journal 对应的现实状态并归类；绝不自动重放 mutation。

### 通用约束

- 一个事务只能执行一次；重复请求返回已有结果。
- 批量事务逐项复验和记录，不以汇总成功掩盖失败。
- 尚未产生副作用的失败可以跳过并继续处理相互独立的项目。
- 任一项目进入 `uncertain` 后，事务立即停止尚未开始的副作用，避免扩大未知影响。
- 取消只影响尚未开始的项目；已执行项目仍必须完成验证和记录。
- 恢复路径按项目声明，不能把“可恢复”概括为整批自动回滚。
- Clear 1.0 不永久删除文件，也不在后台守护中自动创建可执行事务。

### 操作适配

| 操作 | 目标身份与复验 | 成功证据 | 恢复路径 |
| --- | --- | --- | --- |
| 正常退出应用 | PID、启动时间、bundle ID、受保护状态 | 对应进程不再运行 | 用户重新启动应用；1.0 不自动强制结束 |
| 移入废纸篓 | 文件/卷标识、可信根、祖先链、元数据 | 原位置消失且废纸篓目标身份匹配 | 显示最后已知废纸篓位置，由用户恢复 |
| 改变 Clear 自有登录启动 | Clear 自有 `SMAppService` 标识、status 和观测代次 | 系统重新查询为目标 status | 仅当状态没有外部漂移时提供用户触发的相反操作 |
| 卸载应用 | 应用 bundle 身份、运行状态；每个附属项目独立建项 | 应用和选中附属项目逐项移动并复验 | 从废纸篓恢复应用/项目或重新安装；不承诺原子回滚 |

卸载事务必须把应用 bundle 和附属项目作为独立事务项。应用退出是前置条件而非隐藏副作用；用户文档、工程、容器外任意文件默认不进入候选。

## 备选方案

### 每个模块自行实现处理流程

拒绝。它会产生不一致的确认、历史和恢复语义，并增加跨模块安全审计成本。

### 发生失败时自动回滚整批操作

拒绝。退出应用无法还原现场，废纸篓恢复可能与新文件冲突，卸载是多项目非原子操作。虚假的原子性比明确的部分完成更危险。

### 崩溃后自动重试未完成步骤

拒绝。进程外状态可能已经改变，重放会重复副作用。恢复只能 reconcile。

## 影响

- `ClearCore` 需要模块无关的事务模型、journal、摘要绑定、逐项状态和协调器协议。
- `ClearMac` 为每类操作实现目标身份、复验、执行和验证适配器。
- `ClearApp` 使用统一预览、确认、进度、结果和恢复展示。
- 现有磁盘清理计划可迁移为首个适配器，但当前直接执行 API 在迁移完成前不代表最终契约。
- 测试必须覆盖确认失效、身份漂移、部分完成、取消、`uncertain` 停止扩大、崩溃 reconcile 和重复执行。
